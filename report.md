## Задание 1. Параллельный поиск точек множества Мандельброта

### Алгоритм

Комплексная точка `c = real + i·image` проверяется итерациями `z₀ = 0`, `zₙ₊₁ = zₙ² + c` (2.1). Если модуль значения в какой-то момент превысит 2, точка считается не принадлежащей множеству. Если выход за радиус 2 не обнаружен за `MAX_ITER` итераций, точка принимается как принадлежащая множеству в рамках выбранного ограничения числа итераций.

Комплексная плоскость покрывается сеткой `GRID x GRID` на прямоугольнике `real ∈ [-2.0; 0.5]`, `image ∈ [-1.25; 1.25]`. 

Сетка распределяется между потоками по горизонтальным строкам. Потоки обрабатывают строки по очереди: например, при трёх потоках первый поток проверяет строки `0, 3, 6, ...`, второй — `1, 4, 7, ...`, а третий — `2, 5, 8, ...`. Внутри каждой строки поток последовательно проверяет все её точки. Закончив одну строку, поток переходит к следующей закреплённой за ним строке, пока не будет проверена вся сетка или не найдено требуемое количество точек. 

Каждый поток сохраняет найденные точки в собственный буфер `thread_points[my_rank]`. Общий счётчик принятых точек `total_found` защищён мьютексом `count_mutex`. Проверка условия `total_found < npoints` и увеличение счётчика выполняются под тем же мьютексом. После завершения потоков их локальные буферы объединяются в массив `merged`. 

Использовались `GRID = 2000`, `MAX_ITER = 1000`, `npoints = 10000` и число потоков 1, 2, 4 и 8. Каждая конфигурация запускалась 10 раз.

При увеличении количества потоков время выполнения уменьшилось: для восьми потоков получено ускорение примерно в 6,09 раза относительно одного потока. Ускорение не является строго линейным из-за накладных расходов на создание потоков, синхронизацию общего счётчика и различной стоимости проверки точек. Локальные буферы снижают необходимость синхронизации при записи найденных координат, а мьютекс используется для согласованного ограничения общего количества точек.

## Задание 2. Параллельное моделирование задачи N тел

### Алгоритм

Используется двумерная модель движения частиц в плоскости `XY`. Формат входного файла сохраняет семь чисел на тело: массу, координаты `x, y, z` и скорости `vx, vy, vz`. `z` и `vz` считываются, но в расчёте не используются.

Для каждой пары тел с индексами `i < j` сила вычисляется один раз по закону всемирного тяготения (2.2.1). Вклад в силу первой частицы добавляется в её массив, а во вторую частицу добавляется противоположный вектор силы согласно третьему закону Ньютона (`Fpq = -Fqp`). Поэтому число обрабатываемых пар на шаге равно `N(N−1)/2`.

Внешний цикл перебирает индекс `i` первого тела в паре, а значения `i` распределяются между потоками по очереди аналогично первому заданию.

Каждый поток сохраняет вычисленные компоненты сил в собственной части массивов `fx_all` и `fy_all`, доступной через указатели `my_fx` и `my_fy`. После обработки всех пар вклады потоков суммируются, и итоговые компоненты сил для каждого тела записываются в массивы `fx_red` и `fy_red`.

Барьер синхронизирует этапы: 
- запись текущего состояния в CSV, 
- обновление частиц,
- вычисление сил для следующего шага.

## Задание 3. Собственная блокировка чтения-записи

### Алгоритм

#### Структура
Реализована структура `my_rwlock_t`:
- `readers_cond` условная переменная, на которой спят ожидающие читатели;
- `writers_cond` условная переменная, на которой спят ожидающие писатели;
- `active_readers` сколько читателей сейчас работают со списком;
- `waiting_readers` сколько читателей ожидают разрешения войти
- `waiting_writers` сколько писателей ожидают разрешения войти;
- `writer_active` флаг: 1, если сейчас со списком работает писатель, иначе 0;
- `mutex` мьютекс для защиты самих полей блокировки от одновременного изменения разными потоками.

Условные переменные позволяют ожидающим потокам спать до изменения состояния, вместо активного ожидания.

Инициализация происходит через функцию `my_rwlock_init`:

- обнуляет счётчики читателей и писателей;
- устанавливает writer_active = 0;
- инициализирует мьютекс;
- инициализирует обе условные переменные.

Функция `my_rwlock_destroy` освобождает ресурсы условных переменных и мьютекса.


**Блокировка чтения** 

Перед выполнением поиска поток вызывает функцию `my_rwlock_rdlock`. Чтение разрешается, если в данный момент нет активного или ожидающего писателя, в противном случае поток переходит в состояние ожидания. После получения доступа увеличивается счётчик `active_readers`. 
Несколько читателей могут работать со списком одновременно, поскольку поиск не изменяет его содержимое. Ограничение на вход новых читателей при наличии ожидающих писателей не позволяет читателям постоянно обходить писателей и обеспечивает последним приоритет.

**Блокировка записи**

Перед изменением поток вызывает функцию `my_rwlock_wrlock`. Она задерживает поток до тех пор, пока не завершатся все активные читатели и текущий писатель. После этого устанавливается флаг `writer_active`, и поток получает исключительный доступ к списку. Пока писатель активен, другие читатели и писатели должны ожидать.


**Освобождение блокировки** 

После завершения операции вызывается функция `my_rwlock_unlock`. При выходе читателя уменьшается счётчик `active_readers`, а при выходе писателя сбрасывается флаг `writer_active`. Если активных читателей не осталось и есть ожидающие писатели, с помощью `pthread_cond_signal` пробуждается один писатель. Если ожидающих писателей нет, `pthread_cond_broadcast` пробуждает всех ожидающих читателей, поскольку они могут работать одновременно. Условия доступа проверяются в циклах while, так как после пробуждения поток должен повторно убедиться, что состояние блокировки по-прежнему разрешает ему продолжить работу.

### Результаты

В тестовой программе функция поиска `Member` защищается блокировкой чтения, а функции изменения `Insert` и `Delete` — блокировкой записи. Для сравнения использовалась исходная программа с библиотечной `pthread_rwlock_t`. Каждая конфигурация запускалась 10 раз, время усреднялось арифметически.

В первом эксперименте выполнялось 20 000 операций при 1000 начальных элементах: 80% поиска, 10% вставок и 10% удалений.

### Вывод

При одном потоке время выполнения обеих реализаций близко. При двух потоках собственная блокировка показала меньшее время в обоих профилях нагрузки. При четырёх и восьми потоках она оказалась медленнее библиотечной. Вероятными причинами являются конкуренция потоков за общий внутренний мьютекс и дополнительные расходы на пробуждение ожидающих потоков. В собственной реализации ожидающие писатели имеют приоритет перед новыми читателями, что влияет на порядок обслуживания операций. Таким образом, с увеличением числа потоков возрастают расходы на синхронизацию, которые в данном случае снижают производительность собственной блокировки. Стандартная библиотечная реализация лучше оптимизирована для работы при различной нагрузке.
